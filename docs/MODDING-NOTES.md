# Besiege modding notes

Working notes on the parts of Besiege's built-in mod loader this mod relies on,
gathered from the official documentation at
<http://mod.besiege.co.uk/articles/Introduction.html> and from the game's own
assemblies (`Besiege_Data/Managed/`). Recorded here because a few of these are
awkward to find, and one of them is not documented at all.

Target: Besiege on Unity **5.4.0f3**, built-in mod loader (the old third-party
`spaar` loader is deprecated and unrelated).

## Mod structure

A mod is a folder containing `Mod.xml`. The manifest declares metadata plus each
component: `Assemblies`, `Blocks`, `Entities`, `Triggers`, `Events`, `Keys`,
`Resources`. The `ID` element is generated by the game on first load — don't hand
edit it, and don't change it after publishing, or saved machines break.

Manually installed mods go in `Besiege_Data/Mods/`. Workshop subscriptions land in
`steamapps/workshop/content/346010/`.

Useful console commands: `createmod`, `createblock`, `createentity`,
`createassembly`, `addmodsdir`, and `show_logs true` to route all log output to the
in-game console.

## Code: compiled DLL vs ScriptAssembly

Two ways to ship code, both under `<Assemblies>`:

```xml
<Assemblies>
    <Assembly path="SomeAssembly.dll" />        <!-- pre-compiled -->
    <ScriptAssembly path="SomeFolder/" />       <!-- game compiles *.cs at load -->
</Assemblies>
```

`ScriptAssembly` is barely mentioned in the documentation — the exact element name
came out of the `createassembly` command's own template string inside
`Assembly-CSharp.dll`. It compiles every `*.cs` in the named folder and caches the
result in `Besiege_Data/Mods/.CompiledAssemblies`.

### The cache is absolute: a ScriptAssembly is compiled once, ever

`InternalModding.Assemblies.AssemblyCompiler.ResolveScriptAssembly` begins:

```csharp
string path = ModPaths.GetAssemblyPath(container, dir.Name);
if (File.Exists(path)) return path;      // <-- no timestamp check, no hashing
```

There is no comparison against the source files. Once that `.dll` exists the
compiler is never invoked again, so **editing the `.cs` files has no effect at
all** — the game keeps running the build from whenever you first loaded the mod.
This is a nasty one to diagnose, because the symptom is a mod that silently
ignores every change you make and it looks exactly like a bug in your own code.

Two ways out, both in use here:

- `<Debug>true</Debug>` — `InternalModding.Loading.Maintenance` logs
  *"Treating &lt;name&gt; as version change because Debug is enabled"* and calls
  `RemoveCompiledAssemblies` at startup. This is the intended development switch.
- Bumping `<Version>` — the same maintenance pass treats it as a version change.
  This is what invalidates *players'* caches, so a release must bump it.

`tools/install.sh` also deletes the cached `.dll` directly, so an install can
never be a no-op.

### A ScriptAssembly cannot reference another mod

The rest of that method builds the reference list like this:

```csharp
parameters.ReferencedAssemblies.AddRange(
    AppDomain.CurrentDomain.GetAssemblies()
        .Where(a => !string.IsNullOrEmpty(a.Location))
        .Select(a => a.Location).ToArray());
```

Reading that, it looks like a ScriptAssembly could reference any mod already
loaded — and a mod with `<LoadInTitleScreen />` always is. **It does not work.**
Tried it against UI Factory, and got:

```
error 234: The type or namespace name `UI' does not exist in the namespace
`Besiege'. Are you missing an assembly reference?
```

even with UI Factory installed, enabled, and title-screen loaded. The compile
happens inside `AssemblyLoader.LoadMod` → `AssemblyInfo.Resolve()`, in a pass
where other mods' assemblies are not yet in the AppDomain. Whatever the exact
ordering, the empirical answer is that this route is not available.

Corroboration: of the eight mods on this machine that reference `Besiege.UI`,
**all eight ship a pre-compiled `.dll`.** Not one uses a ScriptAssembly. If you
depend on another mod, ship a built assembly — its references bind lazily, when
a type is first touched, by which time the dependency is loaded.

The failure mode when the dependency is genuinely missing is clean either way:
a compile error for a ScriptAssembly, a `ReflectionTypeLoadException` at load
for a pre-built one. The mod does not load; the game is unaffected.

### Hosting the game's Mono: unset TERM first

`tools/besiegecc.c` and `tools/monohost.c` embed Besiege's `libmono.so` to run
its compiler and test code offline. If anything they run touches
`System.Console` — and the compiler does, since it writes diagnostics — Mono's
console initializer builds a terminfo-backed driver whenever stderr is a TTY.
The runtime Unity 5.4 shipped cannot parse a modern terminfo entry, and throws:

```
System.TypeInitializationException (initialising System.Console):
An exception was thrown by the type initializer for System.Console
```

The trap is that it **only happens in a real terminal**. `TERM=xterm-256color`
fails; `xterm`, `dumb` and unset all work, and redirecting the output to a file
or a pipe makes it disappear entirely — so it looks like it works everywhere
until someone runs it in their own shell. Both hosts now call
`setenv("TERM", "dumb", 1)` before `mono_jit_init_version`.

Related: when reporting a managed exception from an embedded host, read the
`message` / `inner_exception` / `type_name` fields directly with
`mono_class_get_field_from_name` + `mono_field_get_value_object` rather than
calling `ToString()`. A failed type initializer leaves the runtime unable to run
more managed code, so `mono_object_to_string` fails too and takes the diagnostic
with it. Field reads execute nothing and still work. Note that the fields live on
`System.Exception`, so walk up with `mono_class_get_parent` — unlike its managed
counterpart, `mono_class_get_field_from_name` does not search base classes.

### The compiler is old

Write C# 4-compatible code. No interpolated strings, no `?.`, no `nameof`, no
expression-bodied members. Passing optional arguments explicitly rather than
relying on defaults is cheap insurance. This holds whether the game compiles the
sources or you do — `tools/build.sh` drives the game's own `mcs.dll` offline, so
the dialect is identical.

## The blacklist

The loader validates mod assemblies and refuses to load ones touching:

- `System.IO` (except `Stream`, `MemoryStream`, `{Binary,Text}{Reader,Writer}`, `Path`, `SeekOrigin`)
- `System.Net`, `System.Xml`
- `System.Reflection`, `System.Runtime.InteropServices`
- `System.Diagnostics` (except `Stopwatch`), `System.Security` (except cryptography)
- `Mono.CSharp`, `Mono.Cecil`, `System.CodeDom.Compiler`, IKVM
- `UnityEngine.WWW`, and the whole `InternalModding` namespace

File access goes through `Modding.ModIO` instead, which is sandboxed to the mod's
own directory. **`System.Xml` being blacklisted is why every data file in this mod
is plain text** — a mod cannot parse its own XML, only the loader can (via
`ModIO.DeserializeXml<T>` for types deriving from `Modding.Serialization.Element`).

`System.Globalization`, `System.Text` and `System.Linq` are all fine.

### `Type.Name` is System.Reflection

The blacklist is enforced per *member*, not per `using`, and the message names the
member rather than your code's intent:

```
[Security] You are not allowed to use
System.String System.Reflection.MemberInfo::get_Name()
(used in ... LevelWatch::PollEntities(...))
[Security] Not loading .../ClippyScripts.dll
Assembly for Clippy did not validate, not loading it!
```

The culprit was `e.GetType().Name` in a log line. `Type` derives from
`MemberInfo`, so `Type.Name` *is* `System.Reflection.MemberInfo.get_Name`, and one
of those in one method rejects the entire assembly. `e.Message` is fine.
`typeof(X)` as an argument is also fine — that is `ldtoken`, not a MemberInfo call.

Compiling proves nothing about this, so `tools/build.sh` runs
`tools/tests/BlacklistCheck.cs` over every build: it walks the IL, resolves each
member reference and fails the build on a forbidden one, printing the member and
the method that used it. Note it reproduces the rules from this document rather
than calling the game's `AssemblyScanner` — that class is public, but it segfaults
outside a Unity player, so it cannot be driven from a command-line host.

## APIs used here

| API | Used for |
| --- | --- |
| `Modding.ModEntryPoint` | `OnLoad`, plus `IsRequiredForMachine` / `IsRequiredForLevel` returning false so saves don't depend on the mod |
| `Modding.Events` | static events for simulation toggle, machine destroyed/loaded/saved, block placed, scene loaded, player join/leave |
| `Modding.ModIO` | reading character packs and tips; writing settings with `data: true` |
| `Modding.ModKeys` / `ModKey` | rebindable hotkeys declared in `<Keys>` |
| `Modding.ModConsole` | user-facing console messages |

`Modding.Game.IsSimulating` exists but touches objects that only exist inside a
level, so this mod tracks simulation state from `Events.OnSimulationToggle`
instead and classifies the rest from `SceneManager.GetActiveScene().name`.

Only the `Modding` namespace is considered stable. Other game classes
(`StatMaster`, `AddPiece`, …) are usable but can change without notice, and this
mod avoids them everywhere except one file — see below.

### `TextGenerator.characters` counts rich text markup

Drawing a box around part of a `Text` means asking `cachedTextGenerator` where
those characters landed. Its `characters` array has **one entry per character of
the string you gave it, markup included** — the entries for a `<size=15>` carry
no width and sit at the position of the glyph after them.

So an index into the layout is an index into the raw string, not into the visible
text. Counting only the characters that get drawn puts every box a tag's length
to the left of what it is meant to be around, which looks exactly like a box
around the first letter of the run: the tag entries pile up at one x with zero
width, so the "run" collapses to a sliver.

### Reading the player's real keybindings

`Modding` exposes no way to ask what a control is bound to, so `Keybinds.cs`
reaches into the game for it. This is the single exception to the rule above.

```csharp
ControlScheme scheme = InputManager.Scheme;   // == OptionsMaster.CustomControls
scheme.Building[…]                            // General Building AdvancedBuilding
                                              // Blocks LevelEditor
```

Each category is a `ControlScheme.ControlEntry[]`; an entry has a `Name` and one
or more `ControlOption`, each holding a `KeyCode[]` chord. The names are the
members of the `ControlScheme.*Controls` enums (`Flip`, `DeleteBlock`, `ToggleUI`)
— an entry gets its name from `entryType.ToString()` in its constructor — and
they are the same strings the game writes into `Besiege_Data/Controls.xml`, which
makes that file a readable map of everything available.

Mod keys need a different route. `Modding.ModKey` keeps `Trigger` and `Modifier`
non-public and offers only "is it down"; the controls screen gets at them through
`ControlScheme.GenerateModControlList(out defaults)`, which converts every loaded
mod's keys into ordinary entries named `"<Mod name>: <key name>"`. That is a
public static, so the mod uses it too.

`InputManager.Scheme` is a plain static field, populated when options load, so it
is readable on the title screen as well as in a level. Everything is still
wrapped: a failure falls back to a table of Besiege's stock bindings, which is
exactly what the tips would have hardcoded otherwise.

### Scene names

From the game's build settings, useful for context detection:

```
INITIALISER, TITLE SCREEN
LevelSelect, LevelSelect2..4, LevelSelectWater, LevelSelectSpace
SANDBOX, BARREN EXPANSE, MISTY MOUNTAIN, WATER SANDBOX, LEGACY SANDBOX, LONE ORB
MasterSceneMultiplayer
1 .. 70           (campaign levels, numbered)

```

The full list is in `Besiege_Data/globalgamemanagers`, as `Assets/Scenes/...`
paths. Campaign levels are the only scenes whose name begins with a digit, which
is what `LevelWatch.IsCampaignLevel` goes on — everything else is named in words.

### God tools are static flags

`StatMaster.GodTools` is a public nested class of public static `bool`s, and it is
what the toolbar buttons themselves read, so there is nothing to hook and no
event — poll it and compare.

```
PyroMode  DragMode  UnbreakableMode  InfiniteAmmoMode  GravityDisabled
ExplodingCannonballs  InfiniteFuel  DisableFire  ExplodeOnClick  HasBeenUsed
```

Remove-bounds is the odd one out: it lives on `StatMaster.Bounding.Enabled`, and
the tool is on when that is **false** (`DisableBoundsButton.IsRuleOn` is the
negation). All of them are reset per level by `GodTools.ResetGodTools()`, so a
watcher has to re-baseline on a scene change or read the reset as the player
switching everything off.

### Besiege does not use `Time.timeScale`

The time slider keeps its own scale on `TimeSlider.Instance.delegateTimeScale`
(public property, 0–2, 1 = normal) and multiplies every delta by hand —
`TimeSlider.DeltaTime()`. `Time.timeScale` is left alone, so reading it tells you
nothing about slow motion. `TimeSlider` is a plain class, not a `MonoBehaviour`,
so `Instance` is an ordinary null check.

Auto mode — where the game slows *itself* to keep a heavy machine stable — moves
the same value, and `TimeSliderView.autoScale` is private. The auto indicator is
not: `SetAuto` does `autoIcon.enabled = b` in the same breath as setting the
flag, and `TimeSliderView.Instance.autoIcon` is a public field. Reading the icon
is how the mod tells "the player slowed time down" from "the game did".

## `LoadInTitleScreen`

Without it, mods load only when the player enters a level or joins a multiplayer
session, so a title-screen overlay is impossible on a fresh boot.

The documentation discourages the flag because it makes a mod undisableable
without a restart. There is a sharper reason to avoid it: a mod with this flag
runs **before the player can reach the mods menu**, so a fatal error in it — a
crash, or a construct that kills the in-game compiler — locks the player out of
Besiege completely, with no in-game way to disable the offending mod. Recovering
means deleting the mod folder by hand.

This mod originally used it, to satisfy "tips on the main menu", and hit exactly
that failure. It now omits it. The assistant loads on entering a level; because
mods are never unloaded, it is present on the main menu from then on — which
covers most of the benefit at none of the risk.

## Resources vs runtime loading

Textures declared in `<Resources>` are loaded by the loader and fetched with
`ModResource.GetTexture(name)`. Every resource must be listed in the manifest up
front, which makes it a poor fit for user-installable content.

For swappable character packs this mod reads PNGs with `ModIO.ReadAllBytes` and
`Texture2D.LoadImage` instead, so a pack is installed by dropping in a folder. The
mod-list icon and workshop thumbnail still go through `<Resources>`, because the
loader needs those before any mod code runs.

## Reading the game's own art and audio

Besiege is Unity 5.4, and its release build strips the type trees out of the
serialized files — so `.assets` files carry no self-description and anything
reading them has to know the layout in advance. These are worth knowing:

- **The object table.** Header is big-endian (`metadataSize`, `fileSize`,
  `version`, `dataOffset`, endianness byte); everything after it follows that
  byte. Besiege's files are format **15**, where each type entry is a class id
  plus a 16-byte hash (and a *second* 16-byte hash first when the class id is
  negative, i.e. a MonoBehaviour), and each object entry is an aligned 8-byte path
  id, `byteStart`, `byteSize`, `typeID`, a 2-byte class id, a 2-byte script type
  index, and — only in 15 and 16 — a trailing `stripped` byte. Miss that byte and
  the table reads as zero objects, which is what it looks like when it goes wrong.
- **Texture2D**, class id 28: name, width, height, complete size, format, mip
  count, two bools, align, image count, dimension, four ints of texture settings,
  lightmap format, colour space, then the pixels — and after them a `StreamData`
  record. Anything sizeable has an empty pixel block and a `StreamData` pointing
  into the `.resS` beside the file, which is where the bytes really are.
- **AudioClip**, class id 83: name, load type, channels, frequency, bits per
  sample, length, `isTrackerFormat` bool, align, subsound index, three more
  bools, align, then the same stream record — source path, 64-bit offset, 64-bit
  size — and a compression format enum (0 PCM, 1 Vorbis, 2 ADPCM, 3 MP3).
- **`GameObject`**, class id 1: a vector of components, and in 5.4 each entry is
  still a *pair* — class id then the `PPtr` — which 5.5 dropped. Then layer and
  name. **`Transform`**, class id 4: owning `GameObject`, rotation, position,
  scale, children, parent. Those two are enough to walk a prefab.

**The level editor's entity thumbnails are pictures of the entities.** Besiege
ships a 256×256 texture per editor entity (`SheepV2`, `PeasantV2`, and so on),
rendered against transparency — which makes them usable as 2D art without
touching a mesh. They are drawn over a drop shadow, and the shadow separates
perfectly: it is pure black at alpha 64, while every pixel of the entity is at
alpha 255.

**Which sounds belong to which entity can be read rather than guessed.** With no
type trees a `MonoBehaviour`'s fields cannot be parsed — but a `PPtr` is a 4-byte
file id followed by an 8-byte path id, so sweeping a component's raw bytes for
path ids that belong to `AudioClip` objects finds its clip references without
knowing the layout. Resolve a non-zero file id through the externals list at the
end of the metadata (index 0 is the file itself). Walk the prefab from its
`GameObject`, do that to every component, and out falls the entity's sound set:
`SheepV2` has a `SoundController` child holding `SheepBleet1..4`, `PeasantV2`
holds `knightHitBleed` and `KnightHitMetal1..3`. `level0` is the level-editor
scene and holds every entity prefab, which makes it the place to look.

**Unity's audio is FMOD's.** The `.resource` files hold a one-sample **FSB5**
bank per clip, not samples: 60-byte header (version 1), then `sampleHeadersSize`
bytes of sample headers, then names, then data. The first sample header is a
64-bit word — bit 0 says more chunks follow, bits 1–4 index a table of rates,
bits 5–6 are channels minus one, bits 7–33 the data offset in 32-byte units,
bits 34–63 the sample count. Mode 2 is PCM16 and unwraps straight into a `.wav`.
Mode 15 is Vorbis and does not: FMOD strips the setup header out of every stream
and shares one copy between them, so decoding needs a lookup table of known
headers keyed by checksum. Roughly a third of Besiege's clips are PCM, including
everything the sheep says.

**`.wav` plays.** `ModResource.CreateAudioClipResource` ends in
`new WWW("file://" + path).audioClip`, which is `AudioType.UNKNOWN` — Unity
infers the format from the extension. So a pack can ship `.wav` as happily as the
`.ogg` the agents use, which is what makes unwrapped PCM usable without an
encoder.

`tools/extract_besiege_art.py` does all of the above. Note what it does *not*
do: ship the result. The art and the audio are Spiderling's, so the packs it
builds are gitignored and rebuilt from each player's own install — the same rule
this repo applies to the Microsoft agents.

## UI layering

Besiege's HUD and menus are uGUI **Screen Space - Overlay** canvases. Unity renders
those after IMGUI, so anything drawn in `OnGUI` ends up *behind* the game's UI —
fatal for a main-menu overlay. Use a `Canvas` with a high `sortingOrder`.

Bonus: uGUI graphics that are raycast targets on a canvas with a
`GraphicRaycaster` are visible to `EventSystem.IsPointerOverGameObject()`, which
the game already checks before acting on a click. That is what stops a click on
the assistant from also placing a block in the world.

## `ModIO` is ambiguous — always fully qualify `Modding` types

Besiege bundles the **mod.io** SDK, which declares a global namespace called
`ModIO` (with `ModIO.API`, `ModIO.UI`, `ModIO.IPlatformIO`, …). That namespace
shadows the `Modding.ModIO` *class*, because C# resolves a name against the
enclosing namespace chain — including the global namespace — before it consults
`using` directives. So this looks right and does not compile:

```csharp
using Modding;

namespace MyMod {
    class Foo {
        void Bar() { ModIO.ExistsFile("x", false); }
        //           ^ binds to the global mod.io namespace, not Modding.ModIO
    }
}
```

```
error 234: The type or namespace name `ExistsFile' does not exist
           in the namespace `ModIO'. Are you missing an assembly reference?
```

Confusingly, `ModIO.IPlatformIO` in the SDK has methods with the same names
(`CreateDirectory`, `GetDirectories`, `DeleteFile`), so the error reads like a
missing method rather than a resolution problem.

A `using ModIO = Modding.ModIO;` alias works only if it is written *inside* the
namespace body — at compilation-unit level the global namespace still wins. This
mod avoids the whole question by fully qualifying every `Modding` type
(`Modding.ModIO`, `Modding.Events`, `Modding.Blocks.Block`, …) and importing no
`Modding` namespaces at all. Besiege also has global classes named `Block`,
`Player` and `Level`, which would shadow `Modding.Blocks.Block` and friends the
same way, so this is worth doing across the board rather than case by case.

Note that `mcs` stops after an `error 234`, so one of these can mask every other
error in the assembly.

The reverse case bites too: a type of *ours* whose name Besiege also uses is
fine everywhere inside `namespace Clippy`, where the nearer declaration
wins, and ambiguous from anywhere outside it. `Clippy.Island` is one —
Besiege has an `Island` of its own — so the headless tests, which live in the
global namespace with `using Clippy;`, have to write
`Clippy.Island.Valfross` in full. The give-away is an error that makes
no sense for a static class of `int` constants:

```
error CS0266: Cannot implicitly convert type `Island' to `int'
```

which is the compiler telling you it found somebody else's `Island`. The mod
itself never sees this, so it only shows up when the tests are built.

## ScriptAssemblies cannot contain `enum` declarations

This is the big one. Besiege's in-game C# compiler **segfaults on any enum
declaration**. Not an error — a SIGSEGV that kills the game process during mod
loading, before it writes anything useful to `Player.log`.

A two-line file is enough to reproduce it:

```csharp
public enum E { A, B }
```

```
at (wrapper managed-to-native) System.Reflection.Emit.TypeBuilder.create_runtime_class
at System.Reflection.Emit.TypeBuilder.CreateType ()
at Mono.CSharp.TypeDefinition.CloseContainer ()
...
Got a SIGSEGV while executing native code.
```

It fails identically regardless of the enum's name, namespace, member count,
explicit underlying type (`: int`), nesting, or compiler flags (`-noconfig`,
`-sdk:2`, with or without any `-r:` references). Equivalent `class` declarations
are fine, so it is specific to emitting enum types through Reflection.Emit in
this Mono build (Unity 5.4.0f3, Linux).

Use int constants instead:

```csharp
public static class Mood
{
    public const int Idle = 0;
    public const int Talk = 1;
    public const int Count = 2;
}
```

…and type the variables as `int`. `switch` over the constants still works, and
an array indexed by the constant replaces `Dictionary<TEnum, V>` nicely.

This only affects ScriptAssemblies. A pre-compiled `<Assembly>` DLL built by a
normal toolchain can contain enums, because the game never compiles it.

`tools/besiegecc` **segfaults if `MANAGED` is not exported**, whatever the source
says. It reads `LIBMONO`, `MANAGED` and `MONOETC` from the environment and does
not check them, so a missing one crashes in `mono_set_dirs` rather than
complaining. `tools/build.sh` exports all three; a probe compiled by hand outside
that script has to as well. This is worth stating plainly because the crash looks
exactly like the enum bug above — it lands on whatever source you happened to be
compiling, which is a fast route to concluding that some innocent language
feature is unsupported. `System.Reflection.Emit` and `-r:Mono.Cecil.dll` both
compile fine.

**Verify before launching.** Because a compile crash locks you out of the game,
`tools/verify-build.sh` runs the game's own compiler offline — it loads Besiege's
`libmono.so` and calls `Mono.CSharp.CompilerCallableEntryPoint.InvokeCompiler` in
`mcs.dll`, the same code path the game uses, so it reproduces these failures on
the command line in about a second.

## Never name a member after its own type

This is legal C# — the spec's "Color Color" rule (§7.6.4.1) explicitly allows a
member and a type to share a name:

```csharp
public enum Mood { Idle, Talk }

public class Tip {
    public Mood Mood = Mood.Talk;   // legal, and Roslyn compiles it fine
}
```

Besiege's in-game Mono compiler recurses forever trying to resolve it. The result
is not a compile error — **the entire game dies with a SIGABRT** partway through
mod loading, having allocated several GB, with nothing written to `Player.log`
after the compiler's assemblies are loaded. The game will not launch at all until
the offending mod is removed, which makes it easy to misread as a broken install.

Rename the member (`Tip.Emotion` here). Worth grepping a mod for the pattern
before shipping:

```
grep -nE '(public|private|protected|internal) +([A-Z]\w*) +\2 *[=;{]' *.cs
```

The same caution applies to a local or parameter named after its own type.

## Besiege shadows four Unity types

Besiege declares public classes in the **global namespace** whose names collide
with Unity's. Because C# checks the global namespace before `using` directives, a
mod that writes `using UnityEngine.UI;` and then `Slider` gets **Besiege's Slider
block**, not the UI widget — with a baffling error like "Type `Slider' does not
contain a definition for `value'", helpfully pointing at `Assembly-CSharp.dll`.

The complete list, from reflecting over the game assembly:

| Unity type | shadowed by a Besiege global class |
| --- | --- |
| `UnityEngine.UI.Slider` | yes |
| `UnityEngine.UI.Scrollbar` | yes |
| `UnityEngine.LOD` | yes |
| `UnityEngine.Particle` | yes |

Nothing else in `UnityEngine`, `UnityEngine.UI` or `UnityEngine.EventSystems`
collides, so `Text`, `Image`, `Button`, `Canvas`, `RawImage` and friends are safe
unqualified. Write `UnityEngine.UI.Slider` in full for those four. This is the
same hazard as `ModIO` above, and the reason this mod fully qualifies every
`Modding` type.

## The block mapper is mesh UI, not uGUI

The panel that appears when you click a block to edit its properties is **not**
uGUI. It is mesh-based UI drawn in world space: `Modding.Mapper.SelectorElements`
hands out `MakeText` (returning a `DynamicText`), `MakeBox` and `MakeTexture`
(returning `MeshRenderer`s) positioned by `Vector3`, and `BlockMapper` places it
via `COMPONENT_Z` / `upperLeft` / `lowerRight`.

`MSlider`, `MToggle` and friends are *data models* (`MapperType` subclasses) with
`Value`/`IsActive` and serialisation — not widgets. The widgets are pooled
`BlockMapperInternal.ParameterWidget` objects bound to a `SaveableDataHolder`,
i.e. to a specific block or entity.

Consequences for a mod that wants a mapper-styled window of its own:

- You cannot reuse the mapper's widgets for non-block settings; they are bound to
  a data holder and to the mapper's own container.
- `SelectorMaterials` (which exposes `LightBackground`, `DarkBackground`,
  `DarkElement`, `RedHighlight`) has a non-public constructor taking
  `InternalModding.Mapper.CustomSelectorReferences` — and `InternalModding` is
  blacklisted for mods, so those materials are only reachable from inside a custom
  mapper selector.

So a standalone panel cannot reuse the machinery, and — because the materials are
unreachable — cannot sample the real colours either. Reproducing the look by hand
gets you close and no closer; this mod tried that first, and the result was a
panel of the wrong shade that was never as transparent as the game's.

The way out is UI Factory 3 (below), which ships those same widgets as ordinary
uGUI prefabs with the colours already baked in.

## Matching Besiege's UI style

Besiege's menus have a recognisable look: a heavy humanist font, capitalised
labels, and buttons that pop slightly on hover and dip on press with a soft
click. All of that can be taken from the running game instead of reproduced.

| What | Where it comes from |
| --- | --- |
| Font | `Berlin Sans FB Demi Bold`, found via `Resources.FindObjectsOfTypeAll<Font>()` |
| Hover / press animation | `ScaleOnMouseOverUI` (game class) |
| Click sound | `SoundOnClickUI` (game class), clip re-hosted on our own AudioSource |
| Capitalised labels | Besiege writes UI text in capitals, e.g. `"BLOCKS"` |

This mod now takes only the font and the capitals rule: once its UI moved onto UI
Factory's prefabs, those brought Besiege's hover, press and click sound with them,
and the code below came out. It is kept here because it is still the answer for
any control you build yourself.

`ScaleOnMouseOverUI` has `objToScale`, `sizeScaler` and `mousePressedScale`, plus
`MouseOver()`/`MouseExit()`/`MouseDown()`/`MouseUp()` which the game drives from
EventTrigger entries. A mod can copy an instance off a real game button with the
documented `ModUtility.CopyComponent`, which brings the game's exact tuning
values along, then point `objToScale` at its own RectTransform and call those four
methods from its own pointer handlers.

Use `Resources.FindObjectsOfTypeAll<T>()` rather than `FindObjectOfType<T>()` to
locate prototypes: a lot of menu UI lives on inactive objects, which the latter
skips.

**Check the font before you trust it with prose.** Besiege writes its UI entirely
in capitals, so its font may be a non-dynamic atlas baked with no lowercase
glyphs. Handing that font a mixed-case sentence renders *nothing* — the result is
a blank panel that reads like a mystery white rectangle, not like a font problem.
Test it, and keep the stock font for body text:

```csharp
bool usable    = font.dynamic || font.HasCharacter('A');
bool lowercase = font.dynamic || (font.HasCharacter('a') && font.HasCharacter('e'));
```

Related: a uGUI `Image` with a null `sprite` draws an **opaque white quad**, so a
texture that failed to load also surfaces as an unexplained white rectangle
rather than as nothing. Default such images to transparent.

One caveat on the click sound: `SoundOnClickUI.audioSource` points at an
AudioSource in whatever scene the prototype came from, so copying the component
verbatim leaves a dangling reference after the next scene load. Copy the *clip*
onto an AudioSource of your own instead.

These are internal game classes, not the stable `Modding` namespace, so a Besiege
update can rename or remove them. Guard every use and fall back to something
built in — the cost of being wrong should be "looks slightly less native", not a
broken mod.

## UI Factory 3

[UI Factory 3](https://gitlab.com/dagriefaa/ui-factory-3) (Workshop item
`2913469777`) ships an asset bundle of Besiege's own uGUI prefabs, plus a JSON
serialiser and an in-game editor. **This mod's interface is built from those
prefabs.** Reproducing the look by hand does not work: the colours and sprites
are not reachable (see the block mapper section above), so a hand-drawn panel is
always an approximation, and it looked like one.

Depending on it means shipping a pre-compiled assembly rather than a
ScriptAssembly — see above. `tools/build.sh` does that with Besiege's own
compiler, so no C# toolchain is needed even so.

### What it gives you

Register nothing; just instantiate. The package name is `"UIFactory3"`:

```csharp
GameObject window = Besiege.UI.Make.Prefab("UIFactory3", "Window", parent);
Sprite triangle   = Besiege.UI.Make.Sprite("UIFactory3", "Triangle");
Font besiegeFont  = Besiege.UI.Make.Font;      // the game's "GOST Common"
```

Prefabs, as registered in `Mod.OnAllResourcesLoaded` (note the names do not all
match the `.prefab` filenames):

| Prefab name | What it is | Default size |
| --- | --- | --- |
| `Window` | Frame + blur + draggable `TopBar` (title, close button) + scroll view | 300×400, bar 50 |
| `Panel` | Plain Besiege-styled `Image` | 100×100 |
| `Text` | `Text` + `LetterSpacing` + `Translator` | 160×30 |
| `Text Button` | `Button` + `ScaleAnimation` + label | 167×38 |
| `Text Toggle` | `Toggle` + full-area checkmark + label | 167×38 |
| `Options` | The mapper-style `< value >` selector | 250×38 |
| `Text Dropdown` | A stock `UnityEngine.UI.Dropdown` in Besiege's skin | |
| `Slider` | `Slider` + handle | 200×32 |
| `Blur`, `Mask`, `Icon`, `Input Field`, `Scroll View`, `Button Dropdown`, `Icon Toggle`, tooltips | | |

`Text Dropdown` is worth knowing about: it is the only stock control here, so its
scrolling list, its click-outside-to-close and its `options` / `value` /
`onValueChanged` are Unity's, already skinned. For a choice out of more than a
handful it beats `Options`, whose arrows step one at a time. Style
`Dropdown.captionText` **and** `Dropdown.itemText` — the latter is the row
template, cloned for every entry — and leave the rest of the template alone.

Both of those labels are **fixed-width rects authored for the prefab's own
width**, exactly like `Options`' `Label` child. Resize the control to fit a row
and the text no longer lines up with it: the caption hangs off the left of its
own background, and rows in the list lose their first letter to the viewport's
edge. Stretch each label (`anchorMin/Max` 0→1) with an inset of a dozen pixels,
and leave the caption's right side clear for the chevron.

Stretching them has a sting in the tail. `ScaleAnimation` — Besiege's swell under
the pointer — scales a rect about its **pivot**, and these are pivoted in the
middle, so a row grows both ways and its left-aligned text slides out past the
inset. The wider you make the rect, the further the same scale carries its left
edge, so fixing the alignment makes the hover worse. `ScaleAnimation.Target` is
public: pivot it on the left edge (and restore `offsetMin`/`offsetMax`, since
moving a pivot moves the rect) to keep the animation without the sideways travel.
`ButtonHoverScale` and `ButtonPressedScale` are **not** public, so the size of
the effect is not yours to tune — only where it grows from.

**Arrows and a list in one row**: spawn `Options`, then spawn `Text Dropdown` as
its child stretched to the slot between the two arrows (`offsetMin.x` and
`-offsetMax.x` of one row height). The arrows are then the real thing — right
sprite, size and hover — and every row built this way lines up with every other
without measuring anything. Two details: hide `Option.label` by **disabling** it
rather than destroying it, because `Option.Index`'s setter writes to that `Text`
without a null check; and make the dropdown's own background transparent instead
of disabling the `Image`, since it is what catches the click that opens the list.

**Adding buttons to a `Window`'s top bar**: the bar is a child called `TopBar` and
its close button a child of that called `CloseButton`. Spawn `Icon Button`s into
the bar beside it. `Icon Button`'s face is a child named `Icon`; set
`preserveAspect` on it, and leave it white so the prefab's own tinting is what
colours it.

Place them by **centres measured in the bar's space**, not by copying the close
button's rect and stepping `anchoredPosition`. Copying works only while the new
buttons are the same size as the old one, and they should not be: the close
button's slot is sized for a letter with room around it, so stepping by its full
width strings the icons out across the bar rather than grouping them in the
corner. Read the close button's box with `GetWorldCorners` +
`InverseTransformPoint` (anchoring-agnostic), then step by the icon size plus the
white space you want, and place each button by its centre. Give them the close
button's **height** even so — bottom edges in one line, and the tooltips hanging
off them line up too.

**Tooltips come in two halves.** `Text Tooltip (Vis Only)` is the panel alone —
background, label, a child called `Triangle` — with no behaviour on it. The
behaviour is `Besiege.UI.Bridge.Tooltip`, and it goes on the **control being
hovered**, not on the panel: point its `TooltipParent` at the panel's
`RectTransform`, hand it the `Triangle`, and set `Direction` (`Tooltip.Dir`)
to the side it should appear on. It fades and slides the panel from wherever the
panel already is — it does not work out a position from the target — so placing
it is the caller's job. Place it before the handler's `Start` runs, which is
free: `Start` is the next frame, and building is this one.

**A tooltip's root is not the bubble you see.** The prefab is a bare holder with
a child called `Background` stretched to `(0,0)-(1,1)` at a size delta of
**40 by 18** — so the bubble reaches twenty pixels past the root on each side and
nine above and below — and the label is a *sibling* of that child, not a child of
it. `Triangle` is inside `Background`, anchored to an edge with a pivot that puts
it outside. Anything to be placed against the bubble's edge has to be anchored
inside `Background`; anchor it to the root and it lands 36 px short of the right
edge, in a box 18 px shorter than the one it appears to be in.

**And the tooltip sizes itself, so you cannot size it.** The root carries a
`VerticalLayoutGroup` (padding 0, spacing 0, no force-expand) and a
`ContentSizeFitter` on preferred size both ways; the label carries a fitter of its
own; `Background` is held out of it all by a `LayoutElement` with `ignoreLayout`.
The root therefore ends up *exactly* the size of the words, and a `sizeDelta`
written onto it is discarded at the next layout pass — silently, which is the
trap. To make room inside one, widen the **layout group's padding**: it is the
only instruction a self-sizing panel takes, it enlarges the panel and keeps the
contents out of the space added in one move, and `Background` follows because it
stretches to the root. Assign a *new* `RectOffset` rather than editing the one
that is there — the setter is what marks the layout dirty.

Those numbers were read out of UI Factory's own asset bundle rather than guessed:
`Resources/besiege-ui-prefabs` is a **UnityFS** bundle whose blocks-info and data
blocks are raw **LZMA** (five props bytes, size known from the block header — feed
`lzma.FORMAT_ALONE` a synthesised 13-byte header). Inside is an ordinary
serialized file, except that a bundle **keeps its type trees**, so the reader that
handles the game's stripped `.assets` files needs to skip them: node count, string
buffer size, 24 bytes per node, then the buffer. `AssetBundle` (class 142) carries
the name→object map, `RectTransform` is class 224, and the fields after the
transform's are anchor min, anchor max, anchored position, size delta, pivot.

Do not parent the panel to the button it explains. `ScaleAnimation` scales the
button on hover, children and all, and hover is exactly when the tooltip is up.
Parent it to whatever holds the button.

**Place it by measuring, not by arithmetic.** Deriving the offset from anchors
and pivots is the obvious approach and it does not work: a prefab's outermost
rect is not necessarily the box you see (the panel can be a child, offset inside
it), and the triangle hangs outside the panel besides, so the result lands
wherever the prefab's internal layout happens to put it — off by its own height,
in this case. What does work:

```csharp
Bounds box = RectTransformUtility.CalculateRelativeRectTransformBounds(parent, panel);
// target rect in the same space, via target.GetWorldCorners + parent.InverseTransformPoint
Vector2 wanted = new Vector2(targetCentreX, targetBottom - gap);
Vector2 actual = new Vector2(box.center.x, box.center.y + box.extents.y);
panel.anchoredPosition += wanted - actual;
```

Bounds cover the panel, its triangle and every offset between them. Anchor the
panel to the same corner as the control (preserving its size across the change:
read `rect.rect.size`, set the anchors, write it back to `sizeDelta`) so the two
stay together if the window is resized afterwards, which it is — this mod sizes
its window to its rows after building them.

Sizing it for more than one line has an ordering trap: `Text.preferredHeight`
is measured against the label's **current** width, so it means nothing until the
panel has been given its final width and the label stretched to it. Width first,
then height. Measure one line by briefly setting the label to a single character
rather than deriving it from the font size — the prefab's authored height is one
line plus its own padding, and that padding is not yours to guess.

Three things about the handler, all read out of its IL:

- **`OnValidate` is public, and in a build you must call it yourself.** It is
  what applies `Direction`, by anchoring and rotating the `Triangle`; Unity only
  calls it in the editor. It also collects the panel's `CanvasRenderer`s and
  hides the panel, so it doubles as the initialiser — do not hand-dim the panel.
- **Hiding means `SetActive(false)`** on the panel, plus alpha 0 on every
  renderer. So measure before calling `OnValidate`, or reactivate around the
  measurement.
- **`ExtendedPosition` is captured on every hover**, not at `Start`: the panel
  rests wherever you left it and slides in from 50 units along `MoveDirection`.
  `Dir.Down` anchors the triangle at `(0.5, 1)` — the panel's top — and slides
  down, so `Down` is the direction the panel sits *in*, not the way it points.

There is **no icon set to draw from**. The bundle's sprites (`Triangle`,
`Square`, `Chevron`, `Knob`, `NMSliderKnob`, `UIMask`, `Pivot`, `UISprite`,
`InputFieldBackground`) are the ones Besiege's own HUD uses — UIFactory scrapes
several of them out of `HUD/TopBar` and `HUD/BottomBar` at load — so anything
like a bin or a plus has to be supplied. Generating it into a `Texture2D` beats
shipping a .png: a few `if`s in a unit square, sampled 4×4 per pixel for the
antialiasing, cost nothing at 64×64 and cannot go missing from an install. Write
the shape with **y running up**, which is the order `SetPixels32` fills.

Draw them as **line art, not silhouettes**, and size them against the close
button's `X` — that X is a letter, so it comes with a letter's white space and a
letter's stroke, and an icon filling its whole button next to it looks like a
different design. Measured off a screenshot, the X is ~40 tall with a ~5.7 stroke
on a button of ~99: hence an icon covering 0.42 of the button, with a stroke
around 0.10 of itself. Preview generated art at the size it will actually be
drawn, downscaled — a shape that reads at 64 pixels can be a smudge at 42.

Better still, **copy an icon the game already has**. Besiege's build menu has a
waste bin; screenshot it, print the bright pixels as characters, and the
proportions come straight off the grid (that one is 52 × 58, five-pixel strokes,
lid overhanging the body, straight walls, three slots). Dividing through by its
height gives numbers that drop into a unit-square shape function unchanged, and
the result belongs in the game's UI in a way a freehand drawing does not.

**Give the popup list an opaque background.** Besiege's panels are translucent by
design — they expect the 3D world behind them. A dropdown opening over a window
stacks one translucent panel on another, and what shows through is not scenery
but the window's own rows, which makes the list unreadable. `C_BG_TOOLTIP` is the
game's answer: the one opaque colour in the palette, opaque precisely because it
backs tooltips, which float over whatever is behind them. Put an `Image` in that
colour on `Dropdown.template` itself — the template is what each popup is cloned
from, so it is set once and it sits behind everything the list draws.

**Several copies of the same overlay**: give each its own canvas one sorting
order apart, and watch for the shared state that only worked because there was
one of everything. Two caught this mod out. A "did the scene change?" helper that
answers by comparing against a stored value answers **the first caller only** —
every other copy is told nothing changed and never catches up; have one of them
ask and let each compare against what it last saw. And a hotkey read
per-instance is acted on per-instance, so a toggle inverts whatever pattern of on
and off happens to exist rather than doing anything a player would predict —
read it once, act on all.

Loading is the other cost: two assistants wearing the same character meant
reading the same megabyte sprite sheet twice, plus the transparent-pixel repaint
each time. A cache keyed by folder fixes it, and is safe here only because
nothing ever destroys a pack's textures — check that before sharing them, since
one `Destroy` would blank the character for everyone else holding it.

Layering is easiest to get wrong once there are several. Anything the player
*opened* should sit above anything that *arrives on its own*, and with one canvas
per copy that is not what happens: copy 2's speech bubble sorts above copy 1's
window, because their canvases do. Give the window a canvas of its own with
`overrideSorting` and a base well above the characters'. That fixes a second bug
for free — a window built before the character is rebuilt ends up an earlier
sibling than it, so its own assistant's bubble would draw over it. **A nested
canvas needs its own `GraphicRaycaster`**, or the thing you just lifted stops
taking clicks. Keep every band, plus the per-copy offset, under 29999:

```
29000 + id   character and speech bubble
29600 + id   options window
29999        the dropdown's click-outside blocker   (not ours)
30000        the dropdown's popup list              (not ours)
```

**Keep your canvas below sorting order 30000 if you use a dropdown.**
`UnityEngine.UI.Dropdown.Show` puts the popup list on its own canvas with
`overrideSorting = true` and `sortingOrder = 30000`, hardcoded — and the blocker
that catches clicks outside it gets 29999. An overlay canvas at 30000 (the
obvious "well above everything" number, and what this mod used) ties with the
popup and wins, so the list is invisible *and* unclickable, which reads as a
dropdown that does nothing. This mod sits at 29000. Nothing in Besiege's own UI
sets `Canvas.sortingOrder` from code — only mod.io's windows and SRDebugger do —
so there is plenty of room down there.

Sprites in the bundle: `Triangle`, `Square`, `Chevron`, `Knob`, `NMSliderKnob`,
`UIMask`, `Pivot`, `UISprite`, `InputFieldBackground`.

`Besiege.UI.Consts` carries the real palette, e.g.
`C_BG_BLACK = (0.03, 0.03, 0.044, 0.2)` — near-black at 20% alpha, which is why
a hand-mixed panel never looked transparent enough.

### Things worth knowing

- **`Make.Prefab` throws if resources are not loaded.** Gate construction on
  `Make.OnReady(package, action)`.
- **`Option.onValueChanged` is `UnityEvent<int>`**, not `<string>`, despite
  `Option.Value` being a string. It reports the index.
- **`Option.options` is a plain field, and assigning it does not redraw the
  label.** Only `Index`'s setter writes `label.text`, so a new list has to be
  followed by `option.Index = index` *even when the index has not changed* —
  otherwise the control keeps showing the placeholder the prefab was authored
  with ("Option A"), which looks exactly like a list that failed to load. Note
  that setting `Index` also fires `onValueChanged`, so guard against reentry.
- **Text on prefabs carries a `Translator`**, which rewrites the text when the
  language changes. Remove it from any label you set yourself.
- **`Make.ScreenCanvas` is recreated on every scene change.** A persistent
  overlay needs its own `DontDestroyOnLoad` canvas; UIF3 prefabs parent into it
  fine.
- **Match the canvas scaler**: UIF3 authors against 1920×1080 with
  `matchWidthOrHeight = 1`. Anything else renders the game's widgets at the
  wrong size next to the game's own.
- The `Window` prefab's scroll view can be deleted if the window is sized to its
  contents; its `TopBar` keeps working, drag included.
- **The press animation eats clicks at a control's edge.**
  `Besiege.UI.Bridge.ScaleAnimation` writes `Target.localScale`, and on UIFactory's
  buttons `Target` is the control's own RectTransform — which is also what the
  raycaster tests. Pressing shrinks the click target out from under the pointer,
  and uGUI only turns a press into a click if the pointer is still over the same
  control when the button comes up. So the outer few percent of every such control
  animates on press and then never fires. It goes unnoticed wherever the artwork
  sits well inside its box (an icon drawn at 42% of a generous button) and is
  obvious wherever the artwork runs to the edge (a 20px icon button, a toggle lit
  across a whole row). The fix is a transparent child with `raycastTarget` on,
  anchored *outside* 0..1 by half the press shrink, so that at the pressed scale it
  still covers the control's resting bounds — proportional anchors mean it survives
  later resizes, and a hit on a child dispatches to the first handler above it.
  Beware applying it to controls that tile: the child reaches past its parent, and
  two of them meeting will argue over the seam. `ButtonPressedScale` is private and
  serialised into the prefab, and reflection is blacklisted, so the shrink has to be
  assumed — assume a deeper press than the prefab uses, since that errs towards a
  generous target rather than leaving part of the bug. Sliders are not affected:
  they act on the press and on dragging, not on the release.
- **A tooltip panel does not need the tooltip handler.** `Text Tooltip (Vis Only)`
  is inert — background, label, triangle — and `Besiege.UI.Bridge.Tooltip` is only
  what opens it on hover. For a panel that has to open on something else, spawn
  the prefab, place it, and toggle `SetActive`: the prefab's own renderers are
  opaque, and it is `OnValidate` → `OnDisable` that hides them. The one thing the
  handler does that is worth copying is the triangle, and it is two assignments —
  `Dir.Up` anchors it to `(0.5, 0)` and rotates it 180°, `Dir.Down` to `(0.5, 1)`
  and 0°, `Left`/`Right` to `(1, 0.5)`/`(0, 0.5)` at 270°/90°.
- **A window sized to its contents needs an edge to grow from.** The prefab is
  pivoted in its middle, which is right for dragging and wrong for resizing: a
  row that appears moves the title bar up by half the row's height, and the
  window slides out from under the pointer that just caused it. Keep the last
  height, and offset `anchoredPosition.y` by half the difference on every resize
  so the top edge holds still and the bottom does the moving. Exempt the first
  pass, or the window opens somewhere other than where it was placed.

## Two transparent Images that overlap composite darker

uGUI draws each `Image` straight onto what is already there, so where two
half-transparent graphics of the same colour overlap, the result is
`1 - (1 - a)²`, not `a`. At the panel alpha used here that is 0.92 against 0.72
— 28% darker, and quite visible as a hard-edged patch in the shape of the
overlap.

It bites wherever a shape is built out of more than one graphic. The speech
bubble's tail was a plain triangle pushed back into the bubble far enough for
its base to reach both edges of the corner, and the buried part printed itself
on the bubble as a 169 px² shadow.

There is no flattening to reach for. `CanvasGroup.alpha` scales each child's
alpha separately and children still composite against each other; `RectMask2D`
clips to a rectangle, which "everywhere except the bubble" is not; a real
inverse mask needs a stencil material. The fix is geometric: **make the pieces
abut instead of overlap.** Squaring the bubble corner the tail leaves from and
cutting a matching right-angled notch out of the tail's base drops the shared
area to ~4.5 px², all of it the sub-pixel band where the two antialiased edges
meet. That band cannot be removed while the two are separate graphics — two
coverage ramps meeting will always blend slightly differently from one solid
edge — but at one pixel wide it is not something you notice.

## Things that bit, or nearly did

- `mod.besiege.co.uk` serves the docs over plain HTTP with a broken TLS handshake
  on HTTPS. Fetch it over HTTP.
- Resource loading is case-sensitive on Linux, and several Workshop mods authored
  on Windows fail on it (`Fire.ogg` declared, `fire.ogg` on disk). If a resource
  "cannot be opened", check the case before anything else.
- `ModConsole.RegisterCommand` exists, but its `CommandHandler` delegate isn't in
  the documented API surface and the signature couldn't be confirmed from
  metadata. This mod uses an in-game options panel instead of console commands.
- `Modding.Configuration` persists settings via `XDataHolder`, whose write method
  (`AddValue`) has an unconfirmed signature. Plain text through `ModIO` avoids the
  guesswork.
